How I Built This Website From My Social Media (Using Only Cloud Tools)

A summary of how (with plenty of help from ChatGPT) I turned years of Instagram posts into this website, using Google Drive, Google Colab, and GitHub.

Most people build personal websites by hand-picking photos, writing new text, or dragging things into a site builder. I did not do that, because I had a brain-wave... 😄🧠✨

Instead, in just around a day, I exported my entire Instagram archive, automatically analysed the captions, sorted every image into meaningful sections, and generated the pages of this site programmatically — all without storing anything locally on my laptop.

The whole workflow lives in the cloud, using three main tools:

  • Google Drive — my working filesystem
  • Google Colab — my Python environment
  • GitHub — where the final site is hosted

Colab handles the GitHub syncing between my GitHub repository and a clone stored inside Google Drive. Everything — from downloading my data to publishing this page — happens there.

High-level flow of the whole process
1

Export from Instagram

Request a full Instagram data export from Meta and save the unzipped archive into Google Drive. This gives you all the images plus JSON files describing each post.

2

Build a media catalogue in Colab

Use a Colab notebook to walk through all the JSON files and extract post_datetime, caption, and media URIs into a CSV: one row per image.

3

Classify each image into sections

Scan each caption for keywords (origami, powerlifting, makeup, singing, activism, etc.), count how many hits each category gets, and assign the image to whichever section has the most matches. Origami posts also get finer-grained subsections.

4

Copy images into the site structure

Another script copies each image from the archive into the GitHub repo in Drive, into folders like assets/images/origami/insects/ or assets/images/powerlifting/2022/, based on its section and subsection.

5

Generate HTML pages from the catalogue

Python scripts take the catalogue and turn it into static HTML pages: galleries for each section, plus per-post pages that show all images from the same Instagram post, with their full caption.

6

Sync to GitHub Pages from Colab

From the Colab notebook, I commit changes inside the Drive-backed clone of my repository and push to GitHub. GitHub Pages then serves the updated site.

1. Getting the content: my Instagram export

I started by requesting a full copy of my Instagram data. When the download was ready, I saved and unzipped it directly into Google Drive so I could work on it from Colab.

The archive included:

  • All the images and videos I'd posted
  • JSON files describing each post
  • Timestamps, captions, and other metadata
  • Information about multi-image posts (carousels)

None of this ever had to live on my local computer: Drive is the canonical home for all of it.

2. Building a media catalogue

Next, in a Colab notebook, I wrote a parser that walked through every JSON file and pulled out the pieces I cared about:

  • post_datetime — when the post was created
  • caption — the text I wrote underneath
  • filename_raw — where the image lives in the export
  • json_source — which JSON file it came from

All of that went into a CSV: one row per image. That CSV became my media catalogue, a kind of structured index of my entire Instagram history.

3. Automatically classifying images by topic

Then I taught the catalogue to understand what each image was about.

I created keyword lists for each section:

  • origami — words like fold, tessellation, paper, etc.
  • powerlifting — squat, bench, deadlift, and so on
  • makeup — eyeshadow, lipstick, palettes, brand names
  • singing — song, karaoke, singing
  • activism — trans, racism, protests, and related terms
  • general — everything else

For each caption, the script counted how many keywords matched for each section. Whichever section had the most hits became the assigned category. In cases where two sections tied, I used a simple priority list as a tiebreaker.

Origami posts got an extra layer of classification into subsections like insects, tessellations, curved, and modular, again based on keywords.

4. Copying images into the GitHub repo

Once each image knew its section and subsection, another Colab script copied the files from the Instagram export into the cloned GitHub repository stored in Google Drive.

It built a folder structure like: 

assets/images/origami/insects/
assets/images/origami/tessellations/
assets/images/powerlifting/2022/
assets/images/makeup/
assets/images/general/

Every run starts by clearing out the old image folders, then repopulating them from the catalogue. That means the repository always reflects the current state of the data.

5. Generating HTML pages automatically

The next step was to turn the catalogue into actual web pages.

I wrote small Python scripts (again in Colab) that read the CSV and generated:

  • An Origami gallery page, split into sections for insects, animals, tessellations, curved origami, modular origami, and general pieces.
  • A Powerlifting gallery grouped by year, so I can see lifting photos chronologically.
  • A Makeup gallery, currently one big grid but ready for future subsections.

For each Instagram post, the catalogue groups all images with the same post timestamp, and creates a dedicated post page. The gallery only shows a single representative thumbnail, but clicking it opens a page with:

  • All images from that post
  • The full caption
  • Any extra context I might add later

6. Pushing changes to GitHub from Colab

The repository itself lives inside Google Drive, so Colab can interact with it just like a local folder. I configured Git with my name and email, added a GitHub personal access token, and then used standard commands: 

!git add .
!git commit -m "Rebuild site from updated media catalogue"
!git push origin main

GitHub sees the new commit, and GitHub Pages takes care of serving the updated site. The whole “rebuild + publish” cycle happens in the browser.

7. Why I like this setup

This approach means the site is:

  • Data-driven – everything comes from a single source of truth: the catalogue.
  • Repeatable – I can rerun the scripts any time and regenerate the whole site.
  • Cloud-based – no local environment to maintain, no files on my laptop.
  • Honest – it’s built out of the content I’ve actually posted over the years.

Now that the foundations are in place, I can add more pages, tweak the styling, or change how things are grouped, and all of it flows from the same underlying data.

And this page you’re reading is part of that: a small write-up generated in the same spirit as the rest of the site.
